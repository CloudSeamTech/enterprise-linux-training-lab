Lane 06 / Performance / Guided scenario

CPU low.
Server slow.

Low CPU does not prove the server is healthy. Work can be waiting for disk, memory, a lock, DNS, a network reply, or another service.

Mission question: What resource or dependency is making the work wait, and what evidence proves it?

00 / Start with the symptom

Define what “slow” means

Imagine a cafeteria. The cooks may be standing still, but lunch can still be late because the freezer door is stuck, plates have not arrived, or the cashier is waiting for the card reader. CPU measures the cooks working. It does not measure every reason the line can stop.

Problem we are answering: Is the whole server slow, one application slow, or one customer path slow? Ask for the affected action, expected time, observed time, start time, frequency, affected users/hosts, and any recent change. Reproduce one safe read-only request if the local procedure permits it. Record the wall-clock start and end.

Good problem statement“On app01.example.test, the approved health request usually returns in 0.3 seconds; since 14:20 UTC it takes 12–18 seconds for all users.”
Bad problem statement“Linux is slow.” It has no action, baseline, scope, timestamp, or measurable target.
Take observations before restarting anything. A restart may remove the evidence and briefly hide a lock, leak, storage stall, or dependency failure.

01 / Establish the shape

Is demand high, and what is the machine doing now?

01

Read load, uptime, and the live overview

Why now: This is the fastest way to learn whether the complaint lines up with high load, a recent boot, busy CPU, idle CPU, I/O waiting, or an obvious process. It is a direction finder, not the final diagnosis.

Terminal · read-only
uptime
top
Every pieceuptime prints current time, time since boot, logged-in user count, and 1/5/15-minute load averages. top opens an updating process view. No flags, arguments, numbers, pipes, redirects, or paths are used here. Press q to leave top.
What mattersCompare load average with logical CPU count; in top, note us, sy, id, wa, memory, swap, process CPU, and process state. Load includes runnable work and uninterruptible waits, so it is not the same as CPU percentage.

Healthy-looking clue

Load is stable for this host, idle CPU is high, I/O wait is near normal, and no single process dominates. This does not close the case; it moves us toward dependencies, latency, or short spikes.

Actionable clue

High wa, load far above the CPU count, low available memory, swap activity, a process in D, or one process consuming resources chooses a focused branch below.

Why next: A live view can miss bursts and averages can blur different causes. Sample counters over time with vmstat.

02 / Sample the system

Is work runnable, blocked, swapping, or waiting?

02

Collect five one-second samples

Terminal · read-only
vmstat 1 5
Every piecevmstat reports process, memory, paging, I/O, system, and CPU counters. The first 1 is a one-second interval. 5 asks for five reports. The first line since boot is historical; judge the later interval lines. There are no flags, pipes, redirects, or paths.
What mattersr = runnable tasks; b = blocked tasks; si/so = swap in/out; bi/bo = blocks read/written; us/sy = user/system CPU; id = idle; wa = I/O wait; st = virtual CPU time taken by the hypervisor.

Good pattern

Later samples show r usually at or below CPU capacity, b near 0, si/so at 0, and wa/st near the host’s baseline.

Bad patterns

Persistent b with high wa points to I/O. Nonzero repeated si/so points to active swapping. High r despite “low CPU” suggests sampling mismatch or throttling. High st suggests hypervisor contention.

Decision: High wa/b → inspect devices. Repeated si/so → inspect memory and processes. High st → correlate with the virtualization team using timestamps. Quiet counters → inspect the affected process, sockets, DNS, and logs.

03 / Storage branch

Is a device slow or saturated?

03

Measure extended per-device I/O

Why now: We run this after vmstat suggests blocked/I/O waiting work—or when the application is storage-heavy—so we can identify the device rather than blame “disk” in general.

Terminal · read-only · sysstat package
iostat -xz 1 5
Every pieceiostat reports CPU and device I/O. -x adds extended device metrics. -z hides devices with no activity. 1 means one-second intervals; 5 means five reports. No pipe, redirect, or path is used.
What mattersRead/write throughput and operations give context. await is average request latency. aqu-sz is average queue length. %util shows device busy time, but its meaning varies with parallel devices and storage arrays—never use it alone.

Good relative to baseline

Latency stays near the known normal range, queues remain controlled, and the device is not continuously pressured during the reproduced slowdown.

Bad relative to baseline

Latency and queue grow during the slow request, often alongside blocked tasks. One busy logical device may map to SAN, virtual disk, multipath, or underlying array work, so preserve the device name and exact time.

Appropriate fix: Match the affected filesystem to its device with approved read-only mapping tools, then correct the proven cause: runaway I/O, filesystem capacity, path failure, storage latency, or workload design. Coordinate vendor/platform work for shared or virtual storage. Do not tune schedulers or delete files just because a number “looks high.”

04 / Memory branch

Is the server reclaiming or swapping memory?

04

Read usable memory and active swap devices

Why now: Low “free” memory alone is normal because Linux uses RAM as cache. We need available memory plus evidence of swap activity from vmstat.

Terminal · read-only
free -h
swapon --show
Every piecefree summarizes memory; -h prints human-readable units such as MiB/GiB. swapon manages or reports swap; --show only displays active swap areas with name, type, size, used, and priority. No pipes, redirects, numbers, or paths are used.
What mattersUse available, not only free. Swap used may be old and harmless; repeated nonzero si/so during the slowdown proves active paging pressure.

Good pattern

Available memory remains comfortable for this workload and vmstat shows no active swap-in/out.

Bad pattern

Available memory is persistently low, si/so repeats, and request latency aligns with paging. Now find which processes consume memory and whether growth is expected.

Decision: Pressure proven → inspect resident memory by process in the next step. No pressure → do not “fix” cache or disable swap; move to process/dependency evidence.

05 / Process branch

Which process is running, waiting, or stuck?

05

Sort processes without changing them

Why now: System counters identified the likely resource. A process list connects that resource to an owner and state.

Terminal · read-only
ps -eo pid,ppid,user,stat,pcpu,pmem,rss,etime,comm --sort=-rss
ps -eo pid,ppid,user,stat,wchan:24,etime,comm --sort=stat
Every pieceps takes a process snapshot. -e selects every process; -o defines columns. pid/ppid are process/parent IDs; user is owner; stat is state; pcpu/pmem are percentages; rss is resident KiB; etime is elapsed time; comm is command name. --sort=-rss sorts largest resident memory first. wchan:24 shows a 24-character kernel wait channel. --sort=stat groups states.
What mattersR = runnable, S = interruptible sleep, D = uninterruptible wait, Z = zombie. A persistent D process plus its wait channel can support an I/O or kernel wait claim. A zombie consumes a process-table entry but no running CPU; its parent must reap it.

Good pattern

Resource use matches the expected workload, states change normally, and no process remains stuck in D across samples.

Bad pattern

One process’s RSS grows, a process dominates CPU, many workers wait in the same channel, or a process remains in D. Preserve PID, owner, state, wait channel, elapsed time, and timestamp.

Appropriate fix: Fix the proven dependency or application cause. Use the service’s documented graceful stop/restart only after evidence capture and impact review. A persistent D process often cannot exit until its kernel wait resolves.

kill -9 sends uncatchable SIGKILL. It gives the process no chance to flush data or clean up and may not remove a task stuck in D. Never normalize it as the first step. Start with diagnosis and the application/vendor’s graceful workflow.

06 / Connection branch

Is the application waiting on a socket or bad network path?

06

Inspect sockets, addresses, and routes

Why now: If CPU, storage, and memory look healthy, the application may be waiting for a database, API, authentication server, or client connection.

Terminal · read-only
ss -tanp
ip -br addr
ip route
Every piecess shows sockets: -t TCP, -a all states, -n numeric names/ports, -p owning process (may require privilege for all owners). ip -br addr uses -br brief output and addr addresses. ip route shows the routing table. No pipes, redirects, numbers, or paths are used.
What mattersLook for the application’s listening port, unusually large groups of SYN-SENT, CLOSE-WAIT, or queued connections, the expected interface/address state, and the route to the named dependency. Socket state is a clue that must be correlated with the application and timestamp.

Good pattern

Expected listener exists, connection states match baseline, interface is up with expected sanitized address, and a valid route selects the expected gateway/interface.

Bad pattern

No listener, repeated outbound connections stuck before establishment, growing connection queues, down interface, or wrong/missing route. Validate ownership and the intended network design before changing anything.

Decision: Local listener absent → inspect service state/logs. Outbound connections stuck → test the named dependency path with approved tools and network owners. Route/interface mismatch → correct the approved configuration, not an ad-hoc temporary route.

07 / Name-service branch

Is name lookup adding the delay?

07

Resolve the dependency the way applications do

Why now: Applications often use hostnames, and a slow primary DNS server or NSS source can add seconds even when the final address is correct.

Terminal · read-only · repeat and time manually
getent hosts db01.example.test
Every piecegetent gets entries through the system Name Service Switch configuration. hosts selects the host database. db01.example.test is a sanitized fake hostname argument. There are no flags, numbers, pipes, redirects, or paths.
What mattersDoes it return the expected documentation address consistently and quickly? A correct answer after a long pause is still a performance failure. Compare repeated timing during good and bad periods; do not publish real internal names.

Good

The expected address returns consistently near the local baseline.

Bad

Long pause, intermittent failure, wrong address, or changing order that the application cannot tolerate. Check approved resolver/NSS configuration and DNS server health with the responsible team.

Appropriate fix: Repair the authoritative record, resolver reachability, or approved NSS ordering that evidence identifies. Do not scatter permanent dependency IPs through /etc/hosts; that creates stale, unmanaged truth.

08 / Correlate evidence

What did services report during the same minute?

08

Read a bounded journal window

Why now: Metrics tell us what resources did; logs may explain why. The window must match the reproduced slowdown so old, unrelated errors do not distract us.

Terminal · read-only · sanitized service
journalctl -u example-app.service --since "2026-08-17 14:19:00" --until "2026-08-17 14:23:00" --no-pager
Every piecejournalctl reads the systemd journal. -u example-app.service limits output to the sanitized unit. --since and --until bound the start/end timestamps; quotes keep each date-time together as one argument. --no-pager prints directly instead of opening a pager. No pipe, redirect, or filesystem path is used.
What mattersLook for timeouts, retries, lock waits, dependency names, storage errors, memory kills, crash/restart messages, and a request ID that matches the symptom. “Error” text outside the incident window is not proof.

Good clue

Normal completion messages and no timing gap for the affected request. Expand to dependency or platform logs using the same bounded window.

Bad clue

A 10-second database timeout aligns with the 12-second request and outbound socket evidence. That correlation supports following the database path.

Decision: Prefer a cause supported by at least two aligned observations—for example latency plus I/O queue, or application timeout plus stuck outbound connections. Do not treat a single scary log line as the cause.

09 / Controlled repair

Make the smallest fix that tests the proven cause

State the evidence, predicted effect, risk, recovery path, owner, and validation before changing production. Preserve vendor-specific procedures for applications, storage, virtualization, backup, and upgrades.

EvidenceAppropriate changeWhyValidation
High device latency/queue aligns with blocked tasks and slow requestsCorrect the proven device/path/workload issue through its approved owner and vendor workflow.It targets the waiting resource rather than CPU, which was not constrained.Repeat the same request and vmstat 1 5/iostat -xz 1 5; latency and user-visible time should return toward baseline.
Active si/so, low available memory, and one growing processCorrect the application leak/configuration or capacity shortfall under change control.It removes the proven source of paging rather than blindly clearing cache or swap.Repeat free -h, vmstat 1 5, process RSS, and the exact user action over a meaningful observation window.
Application timeouts align with DNS delay or outbound connection stallsRepair the named resolver, route, service, or dependency with its owner.The application is waiting outside its CPU execution time.Repeat getent/ss, the application request, and bounded logs; confirm both response time and error recovery.
Avoid these shortcuts: repeated restarts without evidence; kill -9 first; disabling SELinux; disabling TLS; deleting unknown files; rm -rf; clearing caches or swap to make graphs look better; applying automatic STIG remediation without review, testing, and recovery; or calling a VM snapshot a backup.
Close the loop: Run the identical user action with the same scope. Compare before/after duration. Repeat the specific metric that proved the cause. Check for new errors. Watch long enough to cover the original recurrence window. Record the result and any follow-up risk. If the change did not produce the predicted effect, recover or reassess—do not stack another guess on top.
