Class 1

Linux Basics: the daily commands and what every piece means

You do not need hundreds of commands first. Learn how to inspect location, storage, services, logs, networking and software sources without hurting anything.

ls -lah /var/log is like telling a helper: “List the things in this cabinet, show me details, include hidden things, make sizes easy to read, and inspect the /var/log cabinet.” The command is the worker. Flags are extra instructions. The last part is usually the thing/place to work on.
$ pwd

What this does: Shows the folder you are standing in right now.

Pieces: pwd = print working directory.

Why you use it: Before editing/removing files, make sure you are where you think you are.

$ ls -lah

What this does: Lists files with details.

Pieces: -l=long details, -a=hidden files too, -h=easy-to-read sizes.

Why you use it: Daily inspection of permissions, owners, dates, and sizes.

$ df -h

What this does: Shows used/free byte space on mounted filesystems.

Pieces: df=filesystem disk usage; -h=human sizes.

Why you use it: First storage check when a server says it is full.

$ df -i

What this does: Shows inode usage instead of gigabytes.

Pieces: -i=inodes, the little record slots used to create files.

Why you use it: A server can have free GB but still be unable to create files because it has no inode slots left.

$ lsblk -f

What this does: Shows disks, partitions, filesystem types and mount clues.

Pieces: lsblk=list block devices; -f=filesystem info.

Why you use it: Always identify a disk before storage work.

Proof: Match expected device, filesystem and mount.

$ findmnt

What this does: Shows what is actually mounted and where.

Pieces: No flag is required for the basic tree.

Why you use it: If /data was supposed to be a separate disk but is not mounted, an app may fill / instead.

$ du -xhd1 /var | sort -h

What this does: Shows which first-level folders under /var consume space.

Pieces: -x=stay on one filesystem; -h=human sizes; -d1=one level deep; |=hand output to the next command; sort -h=sort human sizes.

Why you use it: Narrow a full filesystem without guessing.

$ lsof +L1

What this does: Finds open files that were deleted from directory listings.

Pieces: lsof=list open files; +L1=links less than 1, meaning deleted-but-still-open files.

Why you use it: Explains why deleting a huge log did not give disk space back.

$ tail -f /var/log/app.log

What this does: Shows the end of a file and keeps watching new lines.

Pieces: tail=end of file; -f=follow.

Why you use it: Watch an application log while reproducing a problem.

$ grep -Rni 'error' /etc/myapp

What this does: Searches files for text.

Pieces: -R=recursive; -n=line numbers; -i=ignore case.

Why you use it: Find config settings or errors quickly.

$ systemctl status sshd

What this does: Shows whether a systemd service is running and recent status.

Pieces: systemctl=service manager; status=inspect, not change.

Why you use it: Know the service state before restarting it.

$ journalctl -u sshd --since '15 minutes ago'

What this does: Shows SSH service logs from a time window.

Pieces: -u sshd=only sshd unit; --since=starting time.

Why you use it: Authentication/service failures usually explain themselves in logs.

$ ss -tlnp | grep :22

What this does: Shows listening TCP sockets and filters for port 22.

Pieces: -t=TCP; -l=listening; -n=numbers; -p=process; pipe sends output to grep.

Why you use it: Proves whether SSH is actually listening.

$ ip -br addr

What this does: Shows interface names and IP addresses compactly.

Pieces: -br=brief.

Why you use it: First network fact: what addresses does this machine actually have?

$ ip route

What this does: Shows where packets will be sent.

Pieces: Routes tell Linux which gateway/interface to use.

Why you use it: Before blaming the firewall, prove the system has a route.

$ getent hosts satellite.example.test

What this does: Uses the system name-service stack to resolve a hostname.

Pieces: getent=get an entry; hosts=hostname database.

Why you use it: Proves DNS/NSS resolution the way applications see it.

$ dnf repolist

What this does: Lists enabled package repositories.

Pieces: dnf=RHEL package manager; repolist=show software sources.

Why you use it: Before installing/updating, know where packages will come from.

$ dnf history

What this does: Lists recent DNF transactions.

Pieces: A transaction is a group of package changes.

Why you use it: Useful after a patch window or when software suddenly changed.

$ rm -rf /path

What this does: Recursively removes a tree and forces removal.

Pieces: rm=remove; -r=walk every subdirectory; -f=force/no prompts.

Why you use it: You will see it in Linux, but it is not a safe shortcut.

Careful: One wrong path can erase an application, configuration, or data tree. Inspect with pwd/ls/find first; avoid this on production unless the removal is specifically approved and verified.

The pipe: |

$ ps aux | grep java

What this does: Find Java processes by sending a process list into a text filter.

Pieces: Left side makes output. | is the pipe. Right side receives that output.

Why you use it: Pipes let you build little tools from simple commands.

Class 2

Break/Fix: common enterprise problems

Scenario A — “The server keeps filling up.”

A trash can keeps filling. Emptying it every hour is not the real fix if someone keeps dumping trash into it. First find which can is full, then what is filling it, then who/process is creating the files.
Check byte space.
$ df -h

What this does: Shows mounted filesystem capacity.

Pieces: -h=easy sizes.

Why you use it: Find which filesystem is near 100%.

Check inode space.
$ df -i

What this does: Shows file-slot usage.

Pieces: -i=inode counts.

Why you use it: Millions of tiny files can cause “no space” even with free GB.

Prove the intended filesystem is mounted.
$ lsblk -f && findmnt

What this does: Shows disks/filesystems, then actual mounts.

Pieces: &&=run second only if first succeeds.

Why you use it: If /data did not mount, the app may be writing into the root filesystem.

Find the large area.
$ sudo du -xhd1 /var | sort -h

What this does: Summarizes one level under /var and sorts by size.

Pieces: -x=one filesystem, -d1=one level, pipe sends to sort.

Why you use it: Narrow the problem from filesystem → directory.

Find giant files.
$ sudo find /var -xdev -type f -size +500M -printf '%s %p\n' | sort -n

What this does: Finds files over 500 MB on the same filesystem.

Pieces: -xdev=do not cross filesystems; -type f=files; -size +500M=larger than 500 MB.

Why you use it: Heap dumps, core dumps, runaway logs and backups often appear here.

Find the process that owns/writes it.

Use the filename with lsof /path/file, check the service logs, and inspect the process. A Java app might repeatedly create .hprof heap dumps after out-of-memory events. A crash may create core dumps. Fix the cause or retention policy rather than only deleting evidence.

If deletion did not return space.
$ sudo lsof +L1

What this does: Finds deleted files still held open.

Pieces: A deleted pathname can disappear while a process still owns the underlying open file.

Why you use it: Restart/rotate the correct service through approved change to release the open handle.

Never start with rm -rf. Confirm the filesystem, directory, file owner/application, retention requirement, and whether the file is needed for evidence/support first.

Scenario B — SSH does not work

$ getent hosts server.example.test

What this does: Resolve the name.

Pieces: Uses configured host/name services.

Why you use it: Prove name → IP.

$ ip route

What this does: Inspect route.

Pieces: Shows default/specific routes.

Why you use it: Prove Linux knows where to send packets.

$ sudo ss -tlnp | grep :22

What this does: Check listening port.

Pieces: TCP + listening + numeric + process.

Why you use it: Prove sshd is bound to port 22.

$ sudo sshd -t

What this does: Validate SSH configuration syntax.

Pieces: -t=test only.

Why you use it: Catch a bad config before reload.

Proof: No output usually means syntax validated.

$ sudo journalctl -u sshd --since '15 minutes ago'

What this does: Read current SSH logs.

Pieces: Unit + time window.

Why you use it: See exact authentication/service errors.

Lesson 3.1 — What you need before installing Satellite

Goal: know the foundation

Satellite 6.19 is supported on RHEL 9 x86_64. Red Hat's installation guidance expects a supported/current RHEL 9 base installation and the required Satellite repositories.

Satellite becomes a dependency for many servers. Bad DNS, bad time, undersized storage or an unsupported OS can turn a content-management problem into an outage later.
$ hostnamectl

What this does: Shows hostname and OS information.

Pieces: No required flag.

Why you use it: Satellite needs a stable FQDN/identity.

$ hostname -f

What this does: Shows the fully qualified domain name.

Pieces: -f=FQDN.

Why you use it: Certificates, URLs and registration depend on the name being correct.

$ getent hosts $(hostname -f)

What this does: Asks DNS/NSS to resolve the Satellite FQDN.

Pieces: $(...) runs a command and inserts its answer.

Why you use it: Prove the name resolves before installation.

$ timedatectl

What this does: Shows clock/time-sync state.

Pieces: No required flag.

Why you use it: Kerberos, TLS/certificates and scheduled content work depend on accurate time.

$ df -h && lsblk -f

What this does: Checks space and block devices.

Pieces: Two inspection commands chained with &&.

Why you use it: Satellite stores databases and a large Pulp content library; plan storage before sync.

Lesson 3.2 — Install a connected Satellite 6.19 server

Where: RHEL shell on the future Satellite server
Register the RHEL host with Red Hat Subscription Management.
$ subscription-manager register

What this does: Registers this server so it can access entitled Red Hat content.

Pieces: The command will prompt for the approved account/registration method in your environment.

Why you use it: The Satellite host itself needs access to installation RPMs.

Enable only the required Satellite installation repos.
subscription-manager repos --disable "*"
subscription-manager repos \ --enable=rhel-9-for-x86_64-baseos-rpms \ --enable=rhel-9-for-x86_64-appstream-rpms \ --enable=satellite-6.19-for-rhel-9-x86_64-rpms \ --enable=satellite-maintenance-6.19-for-rhel-9-x86_64-rpms

Why: Red Hat documents these four repos for Satellite 6.19 on RHEL 9. BaseOS is core OS software; AppStream is additional application content; Satellite is the product software; Satellite Maintenance supplies lifecycle/maintenance tooling.

Patch the base OS and install Satellite RPMs.
$ dnf upgrade

What this does: Updates installed RHEL packages from enabled approved repos.

Pieces: upgrade=bring installed packages to newer available versions.

Why you use it: Red Hat tells you to upgrade packages before installing Satellite.

$ dnf install satellite

What this does: Installs the Satellite software packages.

Pieces: install=add package and dependencies.

Why you use it: This puts the software on disk; it is not configured yet.

Run Satellite's installer.
satellite-installer --scenario satellite \ --foreman-initial-organization "Training_Org" \ --foreman-initial-location "Training_Site" \ --foreman-initial-admin-username satadmin \ --foreman-initial-admin-password 'USE_A_SECURE_PASSWORD'

Pieces: --scenario satellite says configure this machine as Satellite. Initial organization separates business/content ownership. Initial location represents a physical/logical site. Admin username/password creates the first management account.

Do not put real passwords in shell history in production just because the training command shows the option. Follow your organization's secure credential procedure. Also Red Hat warns repeated installer runs can overwrite manual configuration, so document customizations.
Prove Satellite health.
$ hammer ping

What this does: Asks Satellite's major components whether they respond.

Pieces: hammer is Satellite's CLI. ping checks application components.

Why you use it: A successful web login alone is not the only health check.

$ satellite-maintain service status

What this does: Shows Satellite service health.

Pieces: satellite-maintain is Red Hat's maintenance utility.

Why you use it: Know whether application services are up.

Lesson 3.3 — Import the subscription manifest

Where: Satellite Web UI
Content → Subscriptions → Manage Manifest
The manifest is Satellite's permission slip. It tells Satellite which Red Hat subscription content your organization is entitled to see.
Set the correct Organization context in the UI.
Open Content → Subscriptions, click Manage Manifest, choose the exported manifest ZIP, and import it.
If using a connected Hybrid Cloud Console manifest, allocate/add the appropriate subscriptions in Satellite as required by your entitlement model.
Do not casually delete a manifest. Red Hat warns manifest deletion removes entitlements from hosts in that organization.

Lesson 3.4 — Pull Red Hat RPM repositories into Satellite

You do not copy an RPM straight to every customer. First Satellite turns on the approved repository, then synchronizes a local copy of the content/metadata.
Content → Red Hat Repositories
Enable the repositories that match the hosts you manage.

For ordinary RHEL 9 x86_64 package management, BaseOS and AppStream are core repositories. In the UI select package type RPM, find the proper release/architecture repository set, and enable it.

Synchronize.

Open the enabled repository/product and run a sync, or use a Sync Plan for scheduled synchronization. Synchronization copies metadata/packages into Satellite's Library.

Verify content counts and sync status.

A green “sync complete” is not enough if the repository is empty or the wrong release/architecture.

Lesson 3.7 — Create, publish and promote a Content View

Content → Lifecycle → Content Views
A Content View is like taking a picture of the exact approved shelves today. Even if Library changes tomorrow, PROD can stay on the older approved picture until you promote the new one.
Click Create content view; give it a clear name such as RHEL9-Standard.
On Repositories, add BaseOS, AppStream and any approved custom RPM repo the customer needs.
Optional: add filters/dependency solving only when you understand the consequence.
Click Publish new version and describe what changed.
Promote that version to DEV. Validate. Then promote the same version to TEST and PROD when approved.
Proof: open the Content View version and confirm the repositories/packages are present in the intended lifecycle environment.

Lesson 3.8 — Create an Activation Key and register customer servers

An Activation Key is a welcome packet. When a new server arrives, the packet tells Satellite, “this server belongs to this content/lifecycle setup.”
Content → Lifecycle → Activation Keys
Create a key such as rhel9-prod-standard.
Assign the PROD lifecycle environment and the intended Content View.
On Repository Sets, verify the repos customers should receive are enabled/available.
Register the client from Hosts → Register Host. Select the Activation Key, correct Capsule/content source if used, and click Generate.
Run the generated registration command as root on the customer RHEL host. Do not copy a fake training registration command; the real Satellite generates a short-lived JWT-based command for your environment.
Prove customer access.
$ dnf repolist

What this does: Show repositories the host can consume.

Pieces: The list should point to the approved Satellite/Capsule content.

Why you use it: Prove registration/content assignment worked.

$ dnf info example-package

What this does: Ask whether DNF can see package metadata.

Pieces: Replace with real approved package name.

Why you use it: Proves content visibility before installing.

$ sudo dnf install example-package

What this does: Install from enabled approved repos.

Pieces: DNF resolves dependencies from repositories available to the host.

Why you use it: This is the end-to-end customer test.

Proof: Use a test package/host and change approval in production.

Customer says “the RPM is in Satellite but dnf cannot find it.” Where do you check?
Trace the path backward: correct client → registration/activation key → lifecycle environment → Content View version → repo included → version published/promoted → repo enabled → package architecture/release/filter → client cache. “Exists in Library” does not mean “available in PROD.”

Lesson 3.11 — Disconnected / air-gapped Satellite content

If the secure school has no road to the public warehouse, you use an approved delivery truck. A connected staging Satellite exports a sealed shipment; the approved transfer process moves it; the disconnected Satellite imports it.

Satellite 6.19 supports export/import for Yum and Docker content. For disconnected Satellite-to-Satellite transfer, use importable exports when both sides use the supported compatible version; Red Hat also provides syncable Yum exports.

$ hammer content-export complete version --content-view="RHEL9-Standard" --version=1.0 --organization="Training_Org"

What this does: Creates a complete export of a Content View version.

Pieces: Content View + version + organization identify the exact approved shipment.

Why you use it: Move curated content to a disconnected Satellite.

$ hammer content-export incremental version --content-view="RHEL9-Standard" --version=2.0 --organization="Training_Org"

What this does: Exports only changes after a previous export chain.

Pieces: incremental reduces transfer size after a base export.

Why you use it: Useful for routine disconnected updates.

$ hammer content-import version --organization="Training_Org" --path="/var/lib/pulp/imports/EXPORTED_VERSION_DIR"

What this does: Imports a transferred Content View export.

Pieces: Path points to the transferred export directory.

Why you use it: Make disconnected Satellite Library/Content View aware of the shipment.

Do not invent your own USB/file-transfer route for a classified or controlled network. The course teaches the Satellite mechanism; the actual media transfer must follow the site's approved cross-domain/removable-media/content-transfer process.

Lesson 3.12 — Satellite enterprise backup

A VM snapshot is a quick “undo bookmark.” A Satellite backup is a real copy of Satellite's application data/content/configuration made using Red Hat's supported maintenance tool. Enterprise recovery may use both, but they are not the same thing.
$ satellite-maintain backup offline /var/satellite-backup

What this does: Creates a full offline Satellite backup including associated data/content/configuration.

Pieces: offline shuts down Satellite services for consistency; the last argument is the destination.

Why you use it: Red Hat's supported full backup before major work.

Proof: A time-stamped backup directory is created; verify it and move/protect it per policy.

$ satellite-maintain restore /var/backup_directory

What this does: Restores a Satellite backup onto a properly prepared compatible Satellite instance.

Pieces: The path identifies the correct time-stamped backup.

Why you use it: Disaster recovery.

Careful: A backup is not “tested” until the organization has a documented/validated restore procedure. Protect it: backups contain sensitive certificates/keys/configuration.
Red Hat recommends separate storage on a separate system. Offline backup causes downtime, so schedule a maintenance window and make sure other tasks/syncs are not running.

Lesson 4.2 — Preconditions before CAC configuration

$ kinit admin

What this does: Gets a Kerberos ticket for the IdM admin.

Pieces: kinit=initialize Kerberos credentials; admin=principal.

Why you use it: The ipa-advise generation/configuration is an administrative task.

$ klist

What this does: Shows the Kerberos tickets you currently have.

Pieces: No flag required.

Why you use it: Proves kinit worked.

$ openssl x509 -noout -subject -issuer -dates -in issuing-ca.pem

What this does: Reads CA certificate identity and dates.

Pieces: -noout=do not dump encoded cert; subject/issuer/dates select useful fields.

Why you use it: Before trusting a CA file, prove what it actually is.

Lesson 4.3 — Configure every IdM server/replica to accept smart-card auth

Where: shell on each IdM server
Generate Red Hat's configuration script.
$ ipa-advise config-server-for-smart-card-auth > config-server-for-smart-card-auth.sh

What this does: Asks IdM to generate the recommended server configuration script and saves it to a file.

Pieces: ipa-advise=IdM advice/script generator; >=write output to file.

Why you use it: The generated script configures IdM Apache, enables PKINIT on the KDC, updates trust and prepares the IdM Web UI for certificate auth.

Make the script executable.
$ chmod +x config-server-for-smart-card-auth.sh

What this does: Adds execute permission.

Pieces: +x=add executable bit.

Why you use it: Linux must be allowed to run the generated file.

Run it with CA certificates, root first, then intermediates/issuing CAs.
./config-server-for-smart-card-auth.sh root-ca.pem intermediate-ca.pem issuing-ca.pem

Red Hat says pass root CA before sub-CAs. For CAC/DoD certificates, use the CA chain your organization has approved/exported; do not use fake Internet certs.

Repeat on every IdM server/replica that must support certificate authentication.

Red Hat specifically notes new replicas also need this configuration.

Lesson 4.4 — Configure IdM clients for smart-card authentication

Generate on IdM server, execute on each client
$ ipa-advise config-client-for-smart-card-auth > sc_client.sh

What this does: Generates the client-side smart-card setup script.

Pieces: Output redirection stores the script.

Why you use it: The client needs the right packages/trust/auth configuration too.

$ scp sc_client.sh root@client01.example.test:/root/

What this does: Copies the script to a client.

Pieces: scp=secure copy; source first, destination second.

Why you use it: Move the generated configuration to the machine that will authenticate users.

$ sh -x /root/sc_client.sh root-ca.pem intermediate-ca.pem issuing-ca.pem

What this does: Runs the generated client script and prints each command as it executes.

Pieces: sh=shell; -x=trace commands.

Why you use it: Install/configure smart-card support and CA trust on the client.

Red Hat's smart-card tooling also relies on packages such as opensc and the pcscd smart-card daemon.

$ systemctl status pcscd

What this does: Checks the smart-card reader service.

Pieces: pcscd communicates with smart-card readers.

Why you use it: If Linux cannot talk to the card, higher authentication layers cannot work.

Lesson 4.5 — Map the user's CAC certificate to the IdM account

Trusting the badge printer is not enough. The front office still needs to know, “this specific badge belongs to user jane.doe.”

Simple training method: store the user's certificate on the IdM user

$ export CERT=$(openssl x509 -outform der -in user-cert.pem | base64 -w0)

What this does: Converts a PEM certificate to DER and Base64 on one line, then stores it in a shell variable.

Pieces: $(...)=put command output in variable; base64 -w0=one-line encoding.

Why you use it: IdM CLI expects the external certificate in this encoded form.

$ ipa user-add-cert jane.doe --certificate=$CERT

What this does: Adds the certificate to jane.doe in IdM.

Pieces: Username identifies account; --certificate supplies cert data.

Why you use it: Now IdM can link that exact certificate to the user.

Scalable method: certificate mapping data/rules

Large CAC environments usually should not rely on manually pasting every full certificate forever. IdM supports certificate mapping rules/data based on controlled certificate attributes such as issuer/subject. Build those rules from your organization's CAC certificate profile and test carefully; do not copy a generic issuer rule into production.

$ ipa certmap-match user-cert.pem

What this does: Asks IdM which user a certificate would match.

Pieces: The certificate file is the test input.

Why you use it: This is one of the best verification commands before enforcing CAC login.

Proof: Output should return exactly the intended account/domain.

Lesson 4.6 — Prove CAC works before making it mandatory

Do not remove password/fallback authentication first. Prove the card, certificate chain, mapping, SSSD/Kerberos and intended login paths in a test/change window or you can lock administrators out.

Lesson 4.7 — CAC does not equal “STIG complete”

CAC/smart-card authentication helps satisfy identity/authentication requirements, but a RHEL STIG also evaluates logging/audit, SELinux, crypto, permissions, SSH, filesystem mount options, services, packages, time, firewall and many other settings.

SELinux troubleshooting

Normal permissions are a key to the building. SELinux is a security guard inside the building asking whether this kind of process is allowed to touch this kind of file. You need both permission layers.
$ getenforce

What this does: Shows Enforcing/Permissive/Disabled.

Pieces:

Why you use it: Know current mode.

$ ls -lZ /srv/app

What this does: Shows normal permissions plus SELinux context.

Pieces: -Z=security context.

Why you use it: Spot wrong labels.

$ ausearch -m AVC -ts recent

What this does: Finds recent SELinux denials.

Pieces: -m AVC=denial events; -ts recent=recent start time.

Class 9

Bash and cron: scripts explained line by line

A script is a recipe. Bash reads one instruction at a time. Cron is an alarm clock that runs the recipe on a schedule.

A teaching backup script

#!/usr/bin/env bash
set -euo pipefail

SOURCE="/etc"
DEST="/var/backups/etc"
STAMP="$(date +%F_%H%M)"

mkdir -p "$DEST"
tar -czf "$DEST/etc_$STAMP.tar.gz" "$SOURCE"
sha256sum "$DEST/etc_$STAMP.tar.gz" > "$DEST/etc_$STAMP.sha256"
LinePlain meaning
shebangTell Linux which interpreter reads the recipe.
set -euo pipefailMake common failures louder: stop on unhandled command error, unset variables, and pipe failures. It is useful but you still must understand expected nonzero exits.
variablesLabels holding values so paths/names are not repeated everywhere.
$(date ...)Run a command and put its answer inside the variable.
mkdir -pCreate destination and missing parent folders.
tar -czfc=create archive, z=gzip, f=filename follows.
sha256sumCreate a checksum to detect change/corruption.
This is a scripting lesson, not a complete enterprise backup product. Real backups need retention, off-system copies, encryption/access controls, application-consistency and restoration testing.

Cron schedule

0 2 * * * /usr/local/sbin/etc-backup.sh >> /var/log/etc-backup.log 2>&1
FieldMeaning
0minute zero
22 AM
* * *every day-of-month, every month, every day-of-week
>>append normal output to log

Datastore full
