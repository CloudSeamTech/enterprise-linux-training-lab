01 / Mental model

The delivery chain

Satellite is not just a web page full of packages. It is a controlled delivery chain. A package must exist upstream, synchronize, enter a content view, be published, be promoted to the right lifecycle environment, and reach a correctly registered host.

Think of a school supply room. The supplier sends pencils to the warehouse. A teacher approves a box. The box moves to the correct classroom shelf. A student must be on that classroom list before receiving one. “No pencil” can mean a failure at any handoff—not that the whole warehouse is broken.

03 / Guided scenario

Customer cannot pull an RPM

Question: where is the first broken handoff between the host and its approved package content? Start at the customer symptom, then move one layer outward. Do not republish or resynchronize everything before you know which layer failed.

01

Capture the exact request and error

Why now: “Cannot pull RPM” might mean the package name is wrong, no repository offers it, DNS failed, TLS trust failed, or access was denied. The exact error chooses the branch.

Client terminal · read-only
sudo dnf install example-agent
Every piecesudo requests approved elevated execution; dnf manages RHEL packages; install asks DNF to resolve and install; example-agent is a sanitized package name.
Output that mattersRecord whether the message says “No match,” metadata download failure, name resolution failure, certificate error, HTTP 401/403, or timeout.

Good

DNF finds a version and shows a transaction summary. Stop before accepting if this is only a diagnostic check.

Bad

“No match for argument” points toward content/metadata. TLS, DNS, and HTTP errors point toward the transport or access layer.

02

Ask which enabled repository offers the package

Why next: This separates “the package is absent from what this host can see” from an installation-script or dependency problem.

Client terminal · read-only
dnf repolist
dnf --showduplicates list available example-agent
Every piecerepolist lists enabled sources. --showduplicates shows all visible versions. list available searches packages not installed. No pipe or redirect is used, so output is not hidden or written to a file.
DecisionIf the expected repository is missing, inspect host assignment. If present but the package is absent, inspect the promoted content-view version. If visible, return to the exact dependency/script error.
03

Verify the host’s Satellite identity

Why next: A healthy network cannot compensate for a host registered to the wrong organization, lifecycle environment, content view, or Capsule.

Client terminal · read-only
subscription-manager identity
subscription-manager repos --list-enabled

subscription-manager inspects registration; identity prints the registered system identity; repos --list-enabled prints repositories enabled for this host. Compare the UUID and environment to the host record in Satellite Web UI → Hosts → All Hosts → client01.example.test → Content.

Good

The host identity matches Satellite and the expected repository is enabled.

Bad

Unregistered, wrong environment, or missing repo. Correct the assignment through the approved activation-key/host workflow; do not hand-write a random repo file.

04

Prove the content version contains the RPM

Why next: If the client is assigned correctly, the next claim is whether its published and promoted content actually contains the package.

Click path: Satellite Web UI → Content → Content Views → select the host’s view → Versions → select the promoted version → Packages → search for example-agent.

Good

The exact package and needed version appear in the same content-view version promoted to the host’s lifecycle environment.

Bad

The package exists only in Library, another view, or a newer unpromoted version. Review filters, publish a deliberate new version, test it, then promote through the approved path.

Why that fix: Promotion preserves the controlled lifecycle and audit trail. Attaching Library directly would bypass the tested delivery path.

05

Refresh metadata only after the server-side facts agree

Why last: Cleaning metadata is appropriate only when the correct repository and content version are already proven. It should not be used to hide a content-assignment problem.

Client terminal · changes local cache
sudo dnf clean metadata
sudo dnf makecache
dnf --showduplicates list available example-agent

clean metadata removes cached repository metadata, not installed RPMs. makecache downloads fresh metadata. The last command validates visibility without installing anything.

Validated

The expected package version is now listed from the expected Satellite repository.

Still failing

Preserve the error and timestamps. Inspect DNS, route, TLS, proxy/Capsule, and server logs for the same window rather than repeating cache cleanup.

Do not disable certificate checks, paste credentials into shell history, point the host at an unapproved Internet repository, or bulk-promote an untested content view. Those shortcuts remove evidence and bypass enterprise controls.

04 / Container content

The image pull follows a similar chain

For containers, keep four facts separate: the registry hostname, repository path, image tag or digest, and authentication/trust. A successful login does not prove that a requested image path exists.

Client terminal · diagnostic example
getent hosts satellite.example.test
podman login satellite.example.test
podman pull satellite.example.test/approved/tools/example-agent:1.4
Why this ordergetent hosts proves the application-visible name resolution first. podman login tests identity and registry reachability. podman pull finally tests authorization plus the exact path and tag.
What to compareDistinguish DNS failure, certificate trust failure, denied authentication, unauthorized repository access, and “manifest unknown” for a missing tag/path.
Use a credential helper or approved interactive entry. Do not place a password after -p in a shared terminal or script. Do not disable TLS verification as a normal fix; repair the trust chain or registry certificate.

05 / Operations discipline

Boundaries that protect production

Publish/promote everythingChanges many hosts and destroys the clean test boundary.Identify the needed content, publish a deliberate version, test, and promote through environments.
Disable TLS verificationHides identity/trust failures and permits interception.Inspect names, time, certificate chain, and trusted CA; repair the cause.
Assume a VM snapshot is backupA snapshot depends on the original virtual disk and is not an independent recovery copy.Use the Satellite vendor backup/restore workflow and prove recovery according to the local plan.
